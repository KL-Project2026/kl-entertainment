## Phase 9 · investor RBAC 핫픽스 + 35 라우트 격리 테스트 (Phase 8 완료 직후)

> Add Only Rule 은 Phase 0~7 동결 작업의 원칙이었습니다. 동결 이후의 보안 버그 수정은 정상 개발 사이클에 속하며, **prod 배포 전에 반드시 처리**합니다.

### 9-1. RBAC 미들웨어 누락 라우트 전수 스캔

먼저 staff 만의 문제인지 전체 패턴인지 확인. 35 라우트 × investor 토큰 순회 테스트:

```ts
// artifacts/api-server/test/investor-isolation.test.ts (신규)
import { describe, it, expect } from 'vitest';
import request from 'supertest';
import { app } from '../src/app.js';

const INVESTOR_TOKEN = '<investor 로그인 후 발급된 토큰>';

const ALLOWED_ROUTES = [
  '/api/investor/reports',
  '/api/investor/dashboard',
  '/api/auth/me',
  '/api/profile',
];

const ALL_ROUTES = [
  '/api/staff', '/api/branches', '/api/reservations', '/api/rooms',
  '/api/orders', '/api/hostess-profiles', '/api/agents', '/api/agency-mgmt',
  '/api/invoices', '/api/payments', '/api/ledger', '/api/folio',
  '/api/shareholders', '/api/admin/users', '/api/products', '/api/menu',
  // ... 35 개 전수
];

describe('investor isolation — golden rule', () => {
  for (const route of ALL_ROUTES) {
    it(`investor cannot GET ${route} unless explicitly allowed`, async () => {
      const res = await request(app)
        .get(route)
        .set('Cookie', [`kl-auth=${INVESTOR_TOKEN}`]);

      if (ALLOWED_ROUTES.includes(route)) {
        expect(res.status).toBe(200);
      } else {
        expect([403, 404]).toContain(res.status); // 403 권장, 404 도 허용
      }
    });
  }
});
```

**예상 결과**: `/api/staff` 외에도 2~5 개 라우트가 200 으로 떨어질 가능성 있음. 모두 식별.

### 9-2. 공통 RBAC 미들웨어 적용 (가능한 최소 변경)

각 라우트 파일 상단에:

```ts
// artifacts/api-server/src/routes/staff.ts
import { requireRole } from '../middleware/auth.js';

router.use(requireRole(['super_admin', 'admin', 'branch_manager', 'manager']));
// ↑ 이 한 줄로 staff.ts 전체 라우트가 4 개 역할로 제한됨
```

`requireRole` 미들웨어가 없으면 다음 패턴으로 추가:

```ts
// artifacts/api-server/src/middleware/auth.ts
export const requireRole = (allowed: string[]) => (req, res, next) => {
  const role = req.user?.role;
  if (!role || !allowed.includes(role)) {
    return res.status(403).json({ error: 'Forbidden' });
  }
  next();
};
```

### 9-3. 패치 후 격리 테스트 재실행

`pnpm --filter api-server test` → 모든 케이스 PASS 후 다음 Phase 진입.

### 9-4. 감사 로그 1 줄 추가

투자자가 차단된 시도도 audit_log 에 남깁니다 (감사 추적 + 컴플라이언스):

```ts
if (res.status === 403) {
  await db.insert(auditLog).values({
    userId: req.user.id,
    action: 'rbac_denied',
    resource: req.path,
    metadata: { role: req.user.role, attempted: true },
  });
}
```

**Phase 9 완료 조건**: investor 로그인 → `/api/staff`, `/api/hostess-profiles`, `/api/orders`, `/api/agents` 등 모든 운영 라우트 403. 35 라우트 격리 테스트 100% PASS.

## Phase 10 · Supabase 프로젝트 + 스키마 + seed

### 10-1. Supabase 프로젝트 생성

- region: **Singapore (ap-southeast-1)** — KL 에서 가장 가까움 (Tokyo 도 옵션이지만 KL 발 latency 는 SG 가 우위)
- plan: 초기 Free / Pro 결정 — Free는 7일 inactivity pause 라 production 부적합 → **Pro 권장**
- database password 안전한 곳에 저장 (1Password 등)

### 10-2. 연결 문자열 두 개 확보

Supabase Dashboard → Project Settings → Database:

```
# Direct connection (port 5432, 마이그레이션 / pg_dump 용)
DATABASE_URL_DIRECT=postgresql://postgres:[PW]@db.[PROJECT].supabase.co:5432/postgres

# Pooler (port 6543, transaction mode — 앱 런타임용)
DATABASE_URL=postgresql://postgres.[PROJECT]:[PW]@aws-0-ap-southeast-1.pooler.supabase.com:6543/postgres?pgbouncer=true
```

### 10-3. Drizzle 스키마 마이그레이션

```bash
# 마이그레이션은 direct connection 으로 실행 (pgbouncer 는 prepared statement 충돌)
DATABASE_URL=$DATABASE_URL_DIRECT pnpm --filter db migrate

# 또는 Drizzle 명령어
DATABASE_URL=$DATABASE_URL_DIRECT pnpm drizzle-kit push:pg
```

### 10-4. prod-data-seed.sql 실행

```bash
psql "$DATABASE_URL_DIRECT" -f prod-data-seed.sql
```

### 10-5. 검증

```bash
psql "$DATABASE_URL_DIRECT" -c "SELECT COUNT(*) FROM organizations;"  # 1
psql "$DATABASE_URL_DIRECT" -c "SELECT COUNT(*) FROM branches;"
psql "$DATABASE_URL_DIRECT" -c "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='public';"  # 53
```

### 10-6. local 에서 Supabase pooler 로 테스트

`.env` 의 DATABASE_URL 을 pooler URL 로 바꾸고 `./dev.sh` 다시 기동.

> ⚠️ **PgBouncer transaction mode 주의**: Drizzle 의 일부 prepared statement 사용 패턴이 pooler 에서 깨질 수 있습니다. 룸보드·POS·commission 계산 cron job 모두 한 번씩 돌려서 SQL 에러가 안 나는지 확인. 발생 시 해당 쿼리만 direct connection 으로 분리 실행하도록 옵션 설정.

**Phase 10 완료 조건**: local app 이 Supabase pooler 로 정상 작동. 53 테이블 존재. seed 데이터 진입.

## Phase 13 · DNS + Cookie 도메인 + 최종 ALLOWED_ORIGINS

### 13-1. DNS 레코드

도메인 등록업체 (Cloudflare 권장):

```
api.klproject.com    CNAME  <railway-domain>.up.railway.app
app.klproject.com    CNAME  cname.vercel-dns.com
```

> 💡 **Cloudflare 사용 시 Proxy 끄기** (회색 구름). Socket.io WebSocket 이 Cloudflare proxy 와 충돌. DNS only 모드.

### 13-2. Railway / Vercel 에서 custom domain 등록

- Railway → Settings → Networking → Custom Domain → `api.klproject.com`
- Vercel → Settings → Domains → `app.klproject.com`

각각 자동 SSL (Let's Encrypt) 발급 대기 (~5분).

### 13-3. 환경변수 최종 갱신

**Railway:**
```
ALLOWED_ORIGINS=https://app.klproject.com
COOKIE_DOMAIN=.klproject.com
```

**Vercel:**
```
VITE_API_URL=https://api.klproject.com
VITE_SOCKET_URL=https://api.klproject.com
```

각각 재배포.

### 13-4. Cookie SameSite 검증

크로스 사이트 (api.* ↔ app.*) 환경에서:
- Cookie 옵션: `Secure: true`, `SameSite: 'none'`, `Domain: '.klproject.com'`
- 브라우저 DevTools → Application → Cookies 에서 `kl-auth` 확인:
  - SameSite: None
  - Secure: ✓
  - Domain: .klproject.com
  - HttpOnly: ✓

### 13-5. CSP / 헬멧 재검토

helmet 의 default CSP 가 Socket.io 인라인 스크립트를 차단할 수 있음. Phase 0~7 보고에 `contentSecurityPolicy: false` 가 적용됐다면 OK. **추후 별도 CSP 정책 작성 백로그**.

**Phase 13 완료 조건**: `https://app.klproject.com` 정상 접속, login → cookie 발급 → 페이지 이동 시 cookie 유지.

### 14-2. investor 격리 실환경 검증

투자자 계정으로 prod 로그인 → 다음 모두 확인:

- ❌ `/api/agents` GET → 403
- ❌ `/api/orders` GET → 403
